一、文档目的
--------------------------------------------------------------------------------

在「同一 AppID 多渠道换皮 + 运营配置 + 分渠道 KPI」的业务背景下，说明：

  1. 现有前后端已具备什么、缺什么；
  2. 可视化后台应如何分层搭建、部署在哪；
  3. 分阶段要建设哪些模块（配置 / 看板 / 导出 / 运营迁入）；
  4. 与小程序、现有 secret API 如何衔接，避免重复建设。

【架构原则】
  · 渐进演进：不推翻现有 Node 单体，先加 admin 模块与静态 SPA，再按需拆库。
  · 配置与报表同源：channel、branding、promo 进 DB，小程序只读公开 API。
  · 权限与小程序用户隔离：后台账号 ≠ wx_openid Bearer 登录。
  · Phase 1 埋点、Phase 2 上屏：没有 source_channel 字段，后台做了也查不准。

二、现状盘点（As-Is）
--------------------------------------------------------------------------------

2.1 小程序侧（music 仓库）

  | 能力           | 现状                                      | 后台相关缺口        |
  |----------------|-------------------------------------------|---------------------|
  | 用户登录       | Bearer = wx_openid（utils/request.js）    | 无 channel 绑定 API |
  | 主题/开屏      | 本地 theme、splash 静态资源               | 无远程 branding 拉取 |
  | 运营弹窗       | promo-fallback.js + GET /api/promo/active | 配置在服务端 JS 文件 |
  | 意见反馈       | POST /api/feedback                        | 有列表 API 无 UI    |
  | 音乐/贺卡/社区 | 完整业务流                                | 业务表无 source_channel |

2.2 后端侧（backend/src/app.js 单体 ~5000 行）

  技术栈：Express 4、cors、multer、better-sqlite3、axios、fluent-ffmpeg。
  数据：SQLite 单文件（生产在宝塔 Node 进程内）。
  日志：按日滚动 app-YYYY-MM-DD.log / error-YYYY-MM-DD.log。

  已有「半管理」能力（无可视化界面）：

  | 接口 / 模块                         | 鉴权方式                          | 说明                    |
  |-------------------------------------|-----------------------------------|-------------------------|
  | GET /api/feedback?secret=           | FEEDBACK_ADMIN_SECRET             | 分页查 user_feedback    |
  | GET /api/community/admin/posts      | secret 或 x-admin-secret          | 关键词查帖              |
  | DELETE /api/community/admin/post/:id| 同上                              | 删帖                    |
  | src/promo-data.js                   | 无（改文件 + 重启/发版）          | 运营弹窗活动            |
  | scripts/sync-card-templates.js      | x-sync-secret                     | 贺卡模板同步            |
  | GET /api/promo/active               | 公开                              | 小程序拉弹窗配置        |
  | POST /api/promo/event               | 公开/轻量                         | 弹窗曝光埋点            |

  小程序用户鉴权：authMiddleware 校验 Authorization: Bearer {wx_openid}。
  **后台不能使用同一套 Bearer**，必须独立 admin_users + Session/JWT。

2.3 产品结论（摘自 分析 §15）

  · 试点 1～2 家渠道：可暂不做完整后台（secret + SQL + 日志）。
  · 渠道 ≥3、KPI 合同、第三方要看自己的数：**必须上可视化后台**。
  · 推荐路径：**自研轻量 Admin（W2）**，报表层可选 Metabase 等 BI 补充（W4），
    但不能只做 BI——Logo/开屏上下线必须 M1 配置台。

四、需要搭建什么（模块清单）
--------------------------------------------------------------------------------

按优先级与产品文档 M1～M5 对齐。

4.1 M1 渠道与换皮配置（Phase 2 必做 · 最高优先级）

  解决：运营/商务改 Logo、开屏、主题色、功能开关，不再找研发改 DB/JSON。

  后台页面：
    · 渠道列表：channel_id、名称、状态(draft/active/disabled)、合同起止、备注
    · 新建/编辑渠道：基础信息 + Branding 表单
    · Branding 字段（与小程序约定 JSON 结构）：
        splashImageUrl, splashTitle, splashSlogan
        primaryColor, secondaryColor, logoUrl
        features: { showMall, showCommunity, showPromo, ... }
    · 素材上传：复用 POST /api/upload/image（admin 登录后调，或后台专用 upload）
    · 预览说明：生成 path?channel=xxx 与小程序码参数文档
    · 一键启用/禁用：disabled 时 GET /api/branding 返回默认皮或 404+小程序回退

  对外 API（小程序用，公开或轻缓存）：
    GET  /api/branding?channel=xxx
    POST /api/user/channel-bind   （需用户 Bearer，body: { channel }）

  后台 API：
    GET    /api/admin/channels
    POST   /api/admin/channels
    GET    /api/admin/channels/:id
    PUT    /api/admin/channels/:id
    PATCH  /api/admin/channels/:id/status
    PUT    /api/admin/channels/:id/branding
    GET    /api/admin/channels/:id/audit-log

4.2 M2 数据看板（Phase 2 强烈建议）

  解决：内部看 DAU、生成数、贺卡数，按渠道、日期筛选。

  后台页面：
    · 总览卡片：今日 DAU、新增绑定、音乐完成数、贺卡数、反馈数
    · 趋势图：近 7/30 天折线（按 channel 筛选）
    · 渠道对比：表格 Top N

  后台 API：
    GET /api/admin/stats/overview?from=&to=&channel=
    GET /api/admin/stats/timeseries?metric=dau&from=&to=&channel=
    GET /api/admin/stats/channels-ranking?from=&to=

  **依赖 Phase 1 埋点**（见第五节）；无埋点则看板只能做「全站粗统计」。

4.3 M3 报表导出（有 KPI 合同则必做）

  解决：商务每月交付 Excel，避免研发手写 SQL。

  后台页面：
    · 选择渠道、日期区间、指标勾选 → 导出 CSV/XLSX
    · 大表异步：POST 创建任务 → GET 任务状态 → 下载链接

  后台 API：
    GET  /api/admin/export/preview?...        # 前 100 行预览
    POST /api/admin/export/jobs               # 创建导出
    GET  /api/admin/export/jobs/:id
    GET  /api/admin/export/jobs/:id/download

  实现建议：服务端用 exceljs 或 csv-stringify；文件落 uploads/exports/，24h 清理。

4.4 M4 现有能力迁入（Phase 2～3）

  把 secret 查询改为登录后台即可操作：

  | 原能力              | 迁入方式                                      |
  |---------------------|-----------------------------------------------|
  | GET /api/feedback   | Admin 反馈列表页，复用 SQL，adminAuth 替代 secret |
  | community admin     | Admin 社区审核页                              |
  | promo-data.js       | 表 promo_campaigns + Admin CRUD + 缓存刷新    |
  | sync-card-templates | 可选：Admin 触发同步按钮（仍调现有 script 逻辑）|

  迁移策略：**保留旧 secret 接口一个版本周期**，日志打 deprecated，防外部脚本断裂。

4.5 M5 Partner 门户（Phase 3 · 可选）

  第三方登录只看本 channel：
    · 角色 partner，channel_id 写死绑定
    · 仅 M2 只读看板 + M3 导出（本渠道）
    · 可选：本渠道 branding 编辑（需我方审批流，二期再做）

  与内部 Admin 同源：同一 SPA，路由与菜单按 role 过滤。

4.6 Phase 1 必须先做、但不一定有 UI 的部分

  换皮 MVP 无后台时，研发仍需：

    · 建表 channels / channel_branding / user_channel_bindings
    · 业务表加 source_channel（music_tracks、greeting_cards、card_shares、play_history 等）
    · 实现 GET /api/branding、channel-bind
    · 小程序：splash 读 channel、theme 远程覆盖、Storage 持久 mb_channel

  详见 分析 第八～十四节；**这是后台准确性的前置条件**。

五、数据库设计（增量 DDL 建议）
--------------------------------------------------------------------------------

在 initDatabase() 或独立 migrations/001-admin.sql 中追加：

  -- 渠道主表
  CREATE TABLE IF NOT EXISTS channels (
      id TEXT PRIMARY KEY,              -- 如 partner_a，与 query channel 一致
      name TEXT NOT NULL,
      status TEXT DEFAULT 'draft',      -- draft | active | disabled
      contract_start DATE,
      contract_end DATE,
      created_at DATETIME DEFAULT (datetime('now','localtime')),
      updated_at DATETIME DEFAULT (datetime('now','localtime'))
  );

  -- 换皮配置（1:1 或版本化均可；MVP 1:1）
  CREATE TABLE IF NOT EXISTS channel_branding (
      channel_id TEXT PRIMARY KEY,
      splash_image_url TEXT,
      splash_title TEXT,
      splash_slogan TEXT,
      primary_color TEXT,
      secondary_color TEXT,
      logo_url TEXT,
      features_json TEXT,               -- JSON 字符串
      updated_by TEXT,
      updated_at DATETIME DEFAULT (datetime('now','localtime')),
      FOREIGN KEY (channel_id) REFERENCES channels(id)
  );

  -- 用户渠道绑定（最近使用仍保持第三方皮）
  CREATE TABLE IF NOT EXISTS user_channel_bindings (
      user_id TEXT PRIMARY KEY,
      channel_id TEXT NOT NULL,
      bound_at DATETIME DEFAULT (datetime('now','localtime')),
      source TEXT,                        -- qrcode | share | manual
      FOREIGN KEY (user_id) REFERENCES users(id),
      FOREIGN KEY (channel_id) REFERENCES channels(id)
  );

  -- 业务表 ALTER（示例）
  -- ALTER TABLE music_tracks ADD COLUMN source_channel TEXT;
  -- ALTER TABLE card_shares ADD COLUMN source_channel TEXT;

  -- 后台账号（与 users 分离）
  CREATE TABLE IF NOT EXISTS admin_users (
      id TEXT PRIMARY KEY,
      username TEXT UNIQUE NOT NULL,
      password_hash TEXT NOT NULL,        -- bcrypt
      role TEXT DEFAULT 'operator',       -- super | operator | readonly | partner
      partner_channel_id TEXT,            -- role=partner 时必填
      is_active INTEGER DEFAULT 1,
      last_login_at DATETIME,
      created_at DATETIME DEFAULT (datetime('now','localtime'))
  );

  CREATE TABLE IF NOT EXISTS admin_audit_logs (
      id INTEGER PRIMARY KEY AUTOINCREMENT,
      admin_user_id TEXT,
      action TEXT NOT NULL,               -- channel.update | branding.update | ...
      target_type TEXT,
      target_id TEXT,
      detail_json TEXT,
      ip TEXT,
      created_at DATETIME DEFAULT (datetime('now','localtime'))
  );

  -- 运营弹窗（替代 promo-data.js 硬编码）
  CREATE TABLE IF NOT EXISTS promo_campaigns (
      id TEXT PRIMARY KEY,
      payload_json TEXT NOT NULL,         -- 与 promo-fallback 字段对齐
      enabled INTEGER DEFAULT 1,
      priority INTEGER DEFAULT 0,
      updated_at DATETIME DEFAULT (datetime('now','localtime'))
  );

  -- 日聚合（M2 性能；由定时任务写入）
  CREATE TABLE IF NOT EXISTS daily_channel_stats (
      stat_date DATE NOT NULL,
      channel_id TEXT NOT NULL,           -- '' 或 'default' 表示全站默认
      dau INTEGER DEFAULT 0,
      new_bindings INTEGER DEFAULT 0,
      music_completed INTEGER DEFAULT 0,
      cards_created INTEGER DEFAULT 0,
      PRIMARY KEY (stat_date, channel_id)
  );

  -- 可选：原始事件（量大时再上）
  CREATE TABLE IF NOT EXISTS biz_events (
      id INTEGER PRIMARY KEY AUTOINCREMENT,
      event_type TEXT NOT NULL,
      channel_id TEXT,
      user_id TEXT,
      payload_json TEXT,
      created_at DATETIME DEFAULT (datetime('now','localtime'))
  );

指标口径（与 分析 §15.7 一致）：
  · DAU：当日至少一次带 channel 标识的 API 或 dedicated heartbeat
  · 音乐完成：music_tracks.status='completed' AND source_channel
  · 渠道绑定：user_channel_bindings 按日 count

六、Admin API 与鉴权设计
--------------------------------------------------------------------------------

6.1 鉴权方案（推荐）

  方案 A（推荐，单体友好）：Session + HttpOnly Cookie
    POST /api/admin/auth/login  { username, password }
    → Set-Cookie: admin_sid=...; HttpOnly; Secure; SameSite=Strict
    adminAuthMiddleware 查 session 表或 signed cookie

  方案 B：JWT Bearer（适合前后端完全分离部署）
    POST /api/admin/auth/login → { token, expiresIn }
    后续 Authorization: Bearer <jwt>，payload 含 sub, role, channelId

  密码：bcrypt 哈希，禁止明文 env；首个 super 账号用 scripts/seed-admin.js 初始化。

6.2 权限矩阵

  | 角色      | M1 渠道 | M2 看板 | M3 导出 | M4 审核 | M5 本渠道 |
  |-----------|---------|---------|---------|---------|-----------|
  | super     | 全部    | 全部    | 全部    | 全部    | —         |
  | operator  | 编辑    | 全部    | 是      | 是      | —         |
  | readonly  | 只读    | 只读    | 否      | 只读    | —         |
  | partner   | 否      | 本渠道  | 本渠道  | 否      | 可选编辑  |

  实现：requireRole('super','operator') 中间件；partner 强制 SQL WHERE channel_id = req.admin.partnerChannelId。

6.3 与现有 secret API 的关系

  | 旧方式                          | 新方式                    |
  |---------------------------------|---------------------------|
  | ?secret=FEEDBACK_ADMIN_SECRET   | Admin 登录 + /api/admin/feedback |
  | x-admin-secret 社区管理         | /api/admin/community/*    |
  | 改 promo-data.js                | /api/admin/promo/* + DB   |

  环境变量 FEEDBACK_ADMIN_SECRET 可保留作 emergency  break-glass，生产日志告警。

6.4 公开 API 不变性

  小程序继续用：
    · Bearer wx_openid（用户态）
    · GET /api/promo/active（可改为读 DB，响应结构不变）
    · GET /api/branding（新增）

  CORS：admin 域名若与 API 不同源，仅 /api/admin/* 对 admin 域名放行 credentials。

八、统计与定时任务
--------------------------------------------------------------------------------

8.1 聚合策略

  短期（SQLite、日活万级内）：
    · 宝塔「计划任务」每日 01:00 执行 node scripts/aggregate-daily-stats.js

    · 看板读聚合表，避免在线大表 GROUP BY

  中期：
    · 关键动作写 biz_events（music.completed、card.created、app.launch）
    · 小程序可选：启动时 POST /api/event/launch { channel }（轻量）

8.2 日志与监控

  · 保留现有 app/error 日志；Admin 不提供完整日志检索（成本高）
  · M2 可增加「封面上传失败率」：grep error 日志或 biz_events type=cover.upload_fail
  · 告警仍走宝塔/企业微信 webhook（与后台独立）

九、部署与运维（宝塔现状）
--------------------------------------------------------------------------------

9.1 推荐部署拓扑

  域名示例：
    api.lebanhaomian.com     → Node 3000（现有）
    admin.lebanhaomian.com   → 静态 dist + 反代 /api → Node

  Nginx 要点：
    location /api/ { proxy_pass http://127.0.0.1:3000; }
    location / { root /www/wwwroot/admin/dist; try_files $uri /index.html; }

  安全：
    · admin 子域限制 IP 白名单（公司/VPN）
    · 全站 HTTPS
    · 禁止 Admin dist 目录 listing

9.2 发布流程

  1. backend：git pull → npm install（若有新依赖 bcrypt、exceljs）→ pm2 restart
  2. admin-web：npm run build → 覆盖 dist
  3. DB 迁移：首次跑 migrations 或 initDatabase 增量 ALTER
  4. seed-admin.js 仅首次执行

9.3 SQLite 边界（决策 D10）

  · 渠道 <20、并发 admin 用户 <10、日活 <5万：SQLite 足够
  · 导出 Job、聚合 Job 避免与主进程争锁：导出用只读连接或短时 batch
  · 超阈值：迁 PostgreSQL，admin 与 API 连接串分离只读副本做报表

     · 仍 GET /api/promo/active；后端改读 promo_campaigns 表即可，小程序无感

十二、风险与架构决策记录
--------------------------------------------------------------------------------

  R1 单体 app.js 持续膨胀
      → admin 路由拆到 src/admin/*，六个月内不强制微服务。

  R2 secret API 与 Admin 双轨
      → Phase 2 完成后 secret 仅 break-glass，文档标明废弃时间。

  R3 报表不准
      → Phase 1 未埋 source_channel 则禁止对外承诺分渠道 KPI。

  R4 素材合规
      → 渠道 Logo/开屏走微信 imgSecCheck（content-security.js 已支持 MUSIC 凭证）。

  R5 第三方看不到微信外壳品牌
      → 产品层已接受（分析 §三）；后台无法解决 AppID 名称/图标。

  R6 Admin 公网被扫
      → IP 白名单 + 强密码 + 登录失败锁定 + 审计。

十五、结论（架构师摘要）
--------------------------------------------------------------------------------

  1. **要建的是「轻量运营中台」而非大而全 CMS**：核心是 M1 配置 + M2/M3 数。
  2. **后端在现有 Express 单体上扩展 /api/admin/**，SQLite 短期够用，表结构先按渠道埋点设计。
  3. **前端单独 admin-web SPA**，宝塔 Nginx 静态托管 + 反代 API，内网或 IP 限制。
  4. **与小程序契约**：GET /api/branding、channel-bind、source_channel；promo 响应结构不变。
  5. **Phase 1 可以没有 UI，但必须有数据和公开 API**；Phase 2 再把 secret 能力产品化。
  6. **产品细节、角色诉求、待决策项**以 ./分析 第十五、十六节为准；本文侧重实现架构与搭建清单。
